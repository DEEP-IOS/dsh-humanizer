# 设计取舍：为什么 v0.4 加入记忆工作台

v0.4 保留作者声音与内容忠实的方向，补上长期任务缺失的存储、恢复和证据边界。历史上“读全理论、禁止一切工件”的做法无法保证持续理解；当前允许公开交接和内容记忆。[旧版讨论](archive/WHY-v0.3.md)保留当时的推理，但不是现行协议。

## 从无状态工具到连续工作

v0.3 的学习与守卫工具不会记住作品关系与上次进度。对话压缩或重启后，模型依赖仍在上下文中的材料。长篇创作需要显式恢复入口。

prepare 确定作品和任务、恢复相关资料并返回理论；checkpoint 在有实质进展时保存公开交接。它们不要求每段打卡，不自动保存所有聊天，也不以一次“已读”标志永久替代再次读取。

## 为什么先用本机 SQLite 关系图

| 选择 | 收益 | 代价与边界 |
|---|---|---|
| 本机 SQLite | 无额外服务、API Key 或图数据库部署，便于备份 | 单机明文存储，非远程协作服务 |
| 主体—关系—对象加出处 | 可检查关系与证据，支持一跳扩展 | 不自动抽取整部小说 |
| 关键词召回 | 行为可解释，无额外模型调用 | 别名和隐含语义匹配有限，当前加载作品记录再筛选 |
| 阶段与推断标签 | 保留草稿、设想和定稿差异 | 模型仍可能误用，程序不自动判真 |
| revision 修正 | 防止过期覆盖，历史可查 | 需要协调冲突，不能盲重试 |

未来可评估可替换的语义检索，但应以失败案例证明需求，保持无需外部服务的默认路径。增加数据库规模或“图谱”名称不意味着理解增强。

## 为什么记忆不进入 system section

来源资料可能含指令或恶意文字。把它当成系统要求会混淆权限。当前使用动态 user-role context 保留资料身份，并显示出处、阶段与冲突。这不保证提示注入已经彻底解决。

插件自己不调用网络；召回和工具返回会进入模型上下文。实际模型服务可能收到这些内容，本地存储不等于全程离线，详见[安全政策](../SECURITY.md)。

## 为什么不自动覆盖和自动遗忘

新说法可能是草稿、另一个时点或人物的误解。remember 在同 key 中保留候选，revise 需要明确证据和当前版本；跨 key 的语义矛盾仍需核对。

遗忘由用户提出，清除该 key 的历史负载并保留墓碑。宿主日志、其他关系和交接可能还保留引用，不能把“从召回隐藏”宣传成彻底删除一切副本。

## 为什么不只给摘要或强制读全

摘要可能丢失理论条件和反例，读全又可能引入当前不需要的内容。v0.4 选择相关章节全文，允许回查和完整学习。程序不检查模型私有推理，不把返回字数当作理解程度。

## 为什么没有“人味分”

总分难以说明改坏哪句、忘掉什么或为何不忠实。确定性的存储与字符问题交给程序，具体写作判断留给读者与编辑。

这不是拒绝测量：可以统计事实错误、恢复成功率、成本和盲评偏好，但要明确测的是什么。[评估方案](EVALUATION.md)要求固定条件、保留失败和公开限制；目前没有全球排名或成稿优势的实证结论。
